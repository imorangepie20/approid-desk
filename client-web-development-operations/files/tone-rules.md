# 고객 문장 기준

- 첫 문장에 요청 ID, 현재 상태와 고객이 알아야 할 변화를 쓴다.
- 사실, 추정과 결정 요청을 서로 다른 문장으로 나눈다.
- 날짜는 `다음 주`, `곧` 대신 `YYYY-MM-DD`로 쓴다.
- 완료율은 요구사항 항목 수나 테스트 수처럼 계산 근거가 있을 때만 숫자로 쓴다.
- 확인하지 않은 원인, 복구시각, 납품일을 확정형으로 쓰지 않는다.
- 문제가 있으면 영향 범위, 현재 확인된 사실, 다음 확인 행동과 다음 보고시각을 순서대로 쓴다.
- 고객이나 기존 개발자를 탓하는 표현 대신 관찰한 동작과 재현 조건을 쓴다.
- 기술 용어가 필요하면 고객이 해야 할 행동을 같은 문단에 함께 쓴다.
- 요청 범위를 벗어난 내용은 `추가 요청`, 필요한 결정, 예상시간과 견적 필요 여부를 구분해 쓴다.
- 고객의 승인이 필요한 문장은 선택 항목과 답변 기한을 포함한다.
- 비밀번호, 토큰, 세션 값과 전체 접속정보는 이메일·메신저·보고서에 쓰지 않는다.
- 완료 보고에는 구현 항목 수, 실행한 검사와 결과, 운영 URL, 남은 예외와 고객 승인 원문 위치를 쓴다.

## 문장 예시

- 쓰지 않음: `거의 다 됐고 곧 배포될 예정입니다.`
- 사용: `REQ-1042의 승인 요구사항 8개 중 7개를 구현했습니다. 남은 1개는 결제사 테스트 계정이 필요하며, 계정을 2026-09-09까지 받으면 2026-09-10에 검증 결과를 보고하겠습니다.`
- 쓰지 않음: `서버 문제 때문에 늦어졌습니다.`
- 사용: `2026-09-08 14:20부터 배포 서버의 디스크 쓰기 오류를 확인했습니다. 현재 배포를 중단했으며 16:00에 영향 범위와 재개 가능 여부를 다시 보고하겠습니다.`
