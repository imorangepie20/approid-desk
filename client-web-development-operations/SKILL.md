# 고객 웹 개발 운영

## 목적

고객 요청을 빠짐없이 기록하고 합의한 품질과 일정에 맞춰 안전하게 개발·납품한다.

## 언제 쓰는지

- 고객이 신규 홈페이지 제작을 요청했을 때
- 기존 홈페이지의 오류 수정, 기능 추가, 외부 서비스 연동, 자동화 또는 운영 개선을 요청했을 때
- 월 개발 지원 계약의 요청을 접수하고 작업시간을 관리할 때
- 배포 후 버그 수정이나 지속 관리 요청을 처리할 때

## 입력

- 웹 상담: `https://approid.team/#contact`
- 웹 상담 관리: `https://approid.team/admin/consultations`
- 공개 서비스 범위·요금·운영 정책: `https://approid.team/`의 서비스, 진행 방식, 요금, FAQ. 견적 전마다 현재 내용을 다시 확인한다.
- 전화, 이메일, 메신저로 받은 요청: 원문을 보존하고 접수 즉시 상담 관리 시스템에 대신 등록한다. 바로 등록할 수 없으면 요청받은 날 안에 등록한다.
- 상담 시스템 필수 정보: 회사명, 담당자명, 이메일, 업체 유형, 필요한 지원, 희망 상품, 필요한 작업 설명, 개인정보 동의
- 상담 시스템 선택 정보: 전화번호, 사이트 주소, 사용 기술, 희망 일정, 예산
- 기존 홈페이지 작업 필수 자료: 소스와 데이터베이스 접근정보
- 기존 홈페이지 작업 선택 자료: 서버, 도메인, 배포 계정과 관련 문서
- 신규 홈페이지 추가 자료: 사업 목적, 대상 사용자, 필요한 화면과 기능, 기획 내용, 디자인 자료, 문구와 이미지
- 가격 판단 자료: 작업 종류, 기술 난이도, 예상시간, 시간당 단가, 긴급도
- 민감정보: 일반 요청 내용이나 이메일에 적지 않고 시스템의 별도 보안 입력 화면으로만 받는다. 최고 관리자와 최고 관리자가 지정한 관리자만 볼 수 있게 한다.

## 순서

1. 요청을 한곳에 모은다. 웹 요청은 상담 관리 화면에서 확인하고, 전화·이메일·메신저 요청은 같은 날 시스템에 등록한다. 원문, 통화 요약, 첨부파일을 함께 남긴다.
2. 빠진 정보를 확인한다. 기존 홈페이지라면 소스와 데이터베이스 자료가 반드시 있어야 한다. 비밀번호와 접속정보는 보안 입력 화면으로 다시 받는다.
3. 원하는 결과를 쉬운 말로 다시 정리한다. 현재 문제, 바라는 결과, 포함할 일, 포함하지 않을 일, 확인 방법을 고객과 맞춘다.
4. 신규 제작이면 요구사항을 정리한 뒤 기획, 디자인, 문구와 이미지 확정 단계를 거친다. 기존 홈페이지 수정이면 현재 동작과 영향을 받을 기능을 먼저 확인한다.
5. 작업 가능 여부를 판단한다. 필요한 기술 수준과 걸리는 시간을 계산하고, 예산과 일정이 현실적인지 확인한다.
6. 현재 홈페이지의 요금 정책과 내부 금액표를 확인해 견적을 만든다. 작업 범위, 제외 범위, 예상시간, 예정일, 사용할 계약 월을 적는다. 견적 변경은 기존 내용을 덮지 않고 새 버전으로 남긴다.
7. 견적과 진행 조건은 `files/tone-rules.md`에 맞춰 설명한다. 고객과 범위·가격·일정을 합의하고 계약서를 받는다.
8. 계약서에 서명된 것을 확인한 뒤 작업을 시작한다. 처음에는 최고 관리자 한 사람이 분석, 견적, 계약 확인, 개발, 테스트, 배포, 고객 확인을 모두 맡는다.
9. 여러 요청이 있으면 주요 업무 장애의 긴급도, 접수 순서, 납기일 순서로 처리한다. 장기 작업은 `files/update-template.md`와 `files/tone-rules.md`를 사용해 주로 이메일로 주 1회 진행 상황을 보고한다.
10. 합의한 내용만 구현하고 작업 내용과 시간을 매번 기록한다. 고객 책임 시간이 아닌 개발자 귀책 수정도 기록하되 고객 시간에서는 빼지 않는다.
11. 추가 요구가 생기면 원 요청과 연결된 별도 요청으로 등록한다. 난이도와 시간을 다시 계산하고 기본적으로 추가 견적을 만든다.
12. 관련 자동 점검 도구를 실행하고, 실제 사용자의 순서대로 모든 기능을 직접 눌러 확인한다. 바꾼 기능뿐 아니라 영향을 받을 수 있는 기존 기능도 확인한다. Laravel의 초대 전용 가입을 구현하는 작업이면 화면 작성 시 `files/invitation-acceptance-view-template.md`를 사용하고, 로컬 또는 별도 검증 환경에서 `files/verify-invitation-flow.ps1`로 유효한 초대 화면을 확인한다.
13. 실제 업무에서 중대한 방해가 없고 합의한 결과가 나오는지 확인한다. 테스트 결과, 발견한 문제, 수정 내용, 남은 위험을 기록한다.
14. 운영 자료는 하루 한 번 클라우드에 증분 백업한다. 배포 전에 최근 백업 상태와 되돌리는 방법을 확인한다.
15. 배포하고 실제 운영 주소에서 다시 확인한다. 관련 업무에 중대한 지장이 생기면 즉시 이전 정상 버전으로 되돌린다.
16. 고객에게 전화, 이메일 또는 합의한 메신저로 확인을 요청한다. 답변과 승인 내용을 시스템에 남긴다. 답변 기한과 후속 처리는 건별로 관리자가 정하고 이유를 기록한다.
17. 고객이 만족하면 완료로 바꾸고 작업 보고를 보낸다. 원문 요청부터 승인까지 오간 자료와 모든 산출물을 연결해 보관한다.
18. 완료 후에도 요청을 계속 관리한다. 무상 버그 수정 여부는 개발자와 관리자가 건별로 판단하며 기간 제한은 두지 않는다.

## 재사용 파일

- `files/numbers-pull.py`: V1, V2, V5와 V9의 개수를 증거 JSON에서 다시 계산할 때 사용한다. 원본 증거가 없거나 입력 값을 추정해야 하는 경우에는 사용하지 않는다. 입력은 UTF-8 JSON 파일 또는 표준입력으로 전달한다.
- `files/update-template.md`: 7일을 넘긴 작업의 주간 보고나 범위·일정 변화의 중간 보고에 사용한다. 견적서, 계약서, 장애 최초 통보와 완료 보고를 대신하지 않는다.
- `files/tone-rules.md`: 견적 설명, 진행 보고, 장애 보고, 고객 확인 요청과 완료 보고를 쓰기 전에 읽는다. 비밀번호나 토큰 같은 비밀값을 보고문에 넣는 근거로 사용하지 않는다.
- `files/invitation-acceptance-view-template.md`: Laravel Blade와 Flux로 초대 전용 가입 화면을 새로 만들 때 사용한다. 공개 회원가입, React·Vue 화면, 승인된 별도 디자인 시스템이 있는 프로젝트에는 사용하지 않는다. 복사 후 모든 대괄호 자리표시자를 프로젝트 값으로 바꾸고 서버의 초대 검증을 별도로 구현한다.
- `files/verify-invitation-flow.ps1`: Laravel, Docker Compose와 `CreateUserInvitation` 액션을 사용하는 로컬 또는 검증 환경에서 초대 토큰 해시와 HTTP 화면을 확인할 때 사용한다. 운영 환경, 공개 회원가입 방식, Docker Compose를 사용하지 않는 프로젝트에는 실행하지 않는다. 스크립트는 임시 비밀번호를 실행 중에 만들고 검증 데이터를 종료 시 삭제한다.

## 예시

- `examples/`에는 사용자가 만족했다고 확인한 완성 작업만 날짜와 `-good.md` 접미사로 저장한다.
- 승인되지 않은 초안, 진행 중인 결과물과 실패 사례를 좋은 예시로 저장하지 않는다.
- 예시가 있으면 같은 종류의 작업을 시작할 때 가장 최근 파일부터 읽고, 현재 고객의 요구와 충돌하는 내용은 복사하지 않는다.

## 결정

- 신규 홈페이지 제작이면 요구사항 다음에 기획, 디자인, 문구·이미지 확정 단계를 넣는다.
- 기존 홈페이지 수정인데 소스나 데이터베이스 자료가 없으면 착수하지 않고 자료를 요청한다.
- 요청 가격이 현실과 크게 맞지 않거나 요구 일정이 불가능하면 수락하지 않고 가능한 범위·가격·일정을 다시 제안한다.
- 견적은 작업 종류, 기술 난이도, 예상시간, 시간당 단가, 긴급도에 따라 정한다.
- 계약서 서명이 없으면 개발을 시작하지 않는다.
- 고객이 계약 후 내용을 바꾸거나 추가하면 난이도와 시간을 확인하고 기본적으로 별도 견적을 낸다.
- 최초 합의한 기능이 다르게 동작하면 무상 수정으로 본다.
- 고객의 새 요구, 외부 서비스 변경 또는 고객 환경 변경이면 유상 추가 작업으로 본다.
- 주요 업무에 장애가 있으면 가장 먼저 처리하고 1시간 안에 최초 응답한다. 보통 당일 처리를 목표로 하되 확정할 수 없는 복구시간은 약속하지 않는다.
- 여러 일반 요청이 겹치면 접수 순서대로 처리하고, 그다음 납기일을 본다.
- 월 제공시간을 넘기는 작업이면 추가 승인을 받은 뒤 진행한다.
- 견적 승인 시 예상시간을 예약하고, 확정한 작업시간만 실제 사용시간으로 바꾼다. 완료·취소 때 쓰지 않은 예약시간은 돌려준다.
- 월을 넘기는 작업이면 남은 예약을 풀고 다음 달 시간으로 다시 승인받는다. 쓰지 않은 월 시간은 이월하지 않는다.
- 개발자 책임 수정이면 기록은 남기되 고객 시간에서 차감하지 않는다.
- 고객이 답하지 않거나 수정 요청을 반복하면 최고 관리자가 상황별 기한과 다음 상태를 정하고 이유를 남긴다.
- 버그나 납품 지연 가능성이 생기면 즉시 전체 영향을 파악하고 대응 계획을 만든 뒤 고객과 협의한다.
- 배포 후 관련 업무에 중대한 지장이 생기면 수정 작업을 이어가기 전에 정상 버전으로 되돌린다.
- 비밀번호나 접속정보가 이메일·메신저로 오면 일반 기록에 복사하지 않고 보안 입력 화면으로 옮긴다. 이미 노출됐다면 변경을 요청한다.
- 정해지지 않은 테스트 도구, 월 마감 방식, 역할 분담은 최고 관리자가 임시로 결정하고 작업 기록에 남긴다. 임시 결정을 영구 규칙처럼 취급하지 않는다.

## 완료의 정의

### 검증 실행 규칙

- V1부터 V9까지는 고객 개발 요청 한 건을 `순서` 1~18에 따라 처리하고 고객에게 결과물을 보여주거나 완료로 보고할 때만 적용한다.
- `SKILL.md`, `notes.md` 또는 `files/`의 매뉴얼이나 재사용 파일 자체를 수정하는 작업에는 V1~V9를 적용하지 않는다. 이때는 변경한 파일의 형식, 내부 참조, 문법과 실행 결과만 검사하며 진행 중인 고객 프로젝트의 납품 증거를 대신 평가하지 않는다.
- 적용 대상인 고객 개발 요청을 완료로 보고하기 전에 V1부터 V9까지 모두 검사한다.
- 첫 검사에서 `실패`와 `확인 불가`를 합쳐 세 항목 이상이면 수정 작업을 멈춘다. 각 항목을 발생시킨 `순서`의 단계 번호를 찾아 보고하고, 일부 결과만 고쳐서 통과 수를 늘리지 않는다.
- 첫 검사에서 실패와 확인 불가가 두 항목 이하이면 원인을 수정한 뒤 V1부터 V9까지 전부 다시 검사한다.
- 자료가 없거나 접근할 수 없는 항목은 `확인 불가`로 기록하고 통과에 포함하지 않는다. 해당 자료의 소유자, 필요한 자료와 확인하지 못한 이유를 함께 쓴다.
- 최종 보고는 항목마다 한 줄로 작성한다. 형식은 `[통과] V1 — 근거: [기록 ID, 파일 경로, URL, 명령 결과 또는 원문 인용]`, `[실패] V1 — 근거: [...]`, `[확인 불가] V1 — 이유: [...]` 중 하나를 사용한다.

### 검증 항목

1. **V1 요청 원본과 접수 기록 대조**: 전화, 웹, 이메일과 메신저 원본의 개수를 세고 시스템 접수 기록의 개수와 대조한다. 각 접수 기록에 원본 메시지 ID, 파일 경로, 첨부파일 해시 또는 통화기록 ID가 하나 이상 연결되어야 한다. `received_at`과 `registered_at`이 같은 날짜가 아니면 지연 사유 필드가 비어 있지 않아야 한다.
2. **V2 승인 요구사항 충족률 계산**: 고객이 승인한 요구사항 목록의 전체 개수, 구현 완료 개수와 고객이 승인한 제외 개수를 원본 요구사항 파일에서 센다. `(구현 완료 개수 + 승인된 제외 개수) / 전체 개수`가 0.90 이상이어야 하며, 각 항목 ID가 테스트 결과 또는 고객의 제외 승인 원문으로 연결되어야 한다. 증거 JSON이 있으면 `files/numbers-pull.py`의 계산값과 대조한다.
3. **V3 견적·계약·착수 순서 대조**: 최종 견적 버전에 포함 범위, 제외 범위, 예상 분, 금액, 예정일과 사용 계약 월이 모두 있어야 한다. 금액표의 행 ID와 수량으로 금액을 다시 계산해 견적 합계와 일치하는지 확인한다. 계약 서명 시각이 견적 승인 시각 이후이고 첫 작업기록·첫 코드 변경·첫 배포 시각 이전인지 타임스탬프로 대조한다.
4. **V4 요구사항과 변경 결과 연결**: 범위에 포함된 요구사항 ID마다 변경 파일과 줄 또는 커밋 ID, 실행한 테스트 이름과 결과가 연결되어야 한다. 연결되지 않은 포함 요구사항의 개수가 0이어야 한다.
5. **V5 자동 검사와 사용자 경로 확인**: 저장소가 정한 테스트, 형식 검사, 정적 분석과 빌드 명령이 모두 종료 코드 0이어야 한다. 바뀐 사용자 경로마다 실제 URL, 확인 시각과 렌더링 스크린샷 파일을 남긴다. 화면이 없는 API 작업은 요청·응답 본문과 상태 코드가 있는 실행 기록으로 대신한다.
6. **V6 접근권한과 비밀정보 검사**: 로그인 또는 고객사 분리 기능이 있으면 다른 고객사의 직접 URL·파일 ID 접근과 허용되지 않은 역할의 요청이 거부되는 자동 테스트가 실행되어야 한다. 저장소 비밀정보 검사 결과가 0건이어야 하며, 인증 기능이 없는 공개 사이트라면 관리자 경로의 비로그인 응답 상태와 비밀정보 검사 결과를 근거로 남긴다.
7. **V7 배포·백업·복구 확인**: 배포 직전 백업 ID와 생성 시각, 배포 버전 또는 커밋 ID, 롤백 대상 버전을 기록한다. 별도 복구 환경에서 해당 백업을 복원한 실행 기록이 있어야 하고, 운영 URL의 상태 코드와 합의한 확인 문자열 또는 화면 캡처가 배포 결과에 포함되어야 한다.
8. **V8 고객 검수 원문 확인**: 고객의 검수 답변에서 완료 승인 문장 또는 남은 예외를 승인한 문장을 그대로 인용하고 원본 메시지 ID, 채널, 발신자와 시각을 연결한다. 답변이 없거나 구두 답변의 통화기록 ID가 없으면 확인 불가다.
9. **V9 산출물과 진행 보고 개수 대조**: 요청 원본, 분석, 견적 버전, 계약서, 작업기록, 테스트 결과, 배포 기록과 고객 승인 자료의 파일·기록 개수를 종류별로 적고 각 링크가 열리거나 파일이 존재하는지 검사한다. 작업 시작일부터 완료일까지 7일을 넘긴 작업은 경과한 7일 구간 수와 주간 보고 개수가 같아야 하며, 차이가 있으면 실패다. 증거 JSON이 있으면 `files/numbers-pull.py`의 산출물과 주간 보고 개수를 대조한다.

## 예외 사례

- 전화·이메일·메신저 요청을 즉시 등록할 수 없으면 요청받은 날 안에 등록하고 늦어진 이유를 남긴다.
- 고객이 사용 기술을 모르면 기술명을 요구하지 말고 사이트 주소, 현재 문제와 원하는 결과부터 받는다.
- 소스 또는 데이터베이스 접근이 불가능하면 인수 가능 여부를 판단할 수 없다고 알리고 진단에 필요한 자료 목록을 보낸다.
- 턱없이 낮은 예산이나 불가능한 납기라면 억지로 계약하지 않는다. 줄일 범위와 가능한 일정을 제안한다.
- 주요 업무 장애면 일반 순서를 멈추고 1시간 안에 응답한다. 야간·주말 상시 대응이나 복구시간 보장은 별도 계약이 없으면 약속하지 않는다.
- 버그가 생기면 영향 범위와 원인을 먼저 파악하고 수정 계획을 세운 뒤 고객과 협의한다.
- 납품 지연 위험이 생기면 예정일 전에 알리고 원인, 현재 상태, 새 계획, 고객이 선택할 수 있는 대안을 함께 보낸다.
- 고객 요청 변경은 기존 견적을 고치지 않고 새 견적 버전과 승인 기록을 만든다.
- 고객이 검수에 답하지 않으면 관리자가 건별 기한과 처리 상태를 정하고 연락 시도와 판단 이유를 기록한다.
- 배포 후 중대한 업무 장애가 생기면 이전 정상 버전으로 되돌리고, 원인 파악과 재배포는 별도 기록으로 진행한다.
- 무상 수정 기한은 제한하지 않지만, 무상인지 유상인지는 최초 합의 내용과 변경 원인을 근거로 개발자와 관리자가 판단한다.
- 일정 지연, 낮은 품질, 숨긴 문제, 근거 없는 견적, 기록 없는 구두 합의, 고객과의 감정적 다툼은 나쁜 결과다. 즉시 최고 관리자에게 올리고 사실과 합의 중심으로 정리한다.
