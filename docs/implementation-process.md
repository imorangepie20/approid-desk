# Approid Desk 개발 구현 순서

## 문서 목적

이 문서는 고객사의 신규 개발과 유지보수 요청을 접수하고, 견적과 승인, 개발, 검수, 시간 정산, 완료까지 관리하는 Approid Desk의 구현 순서를 정의한다. 각 단계는 앞 단계의 데이터와 권한 규칙을 전제로 하므로 아래 순서대로 개발한다. 각 단계의 완료 조건을 충족하기 전에는 다음 단계의 핵심 기능을 운영 환경에 배포하지 않는다.

## 개발 기준

- 기술 구성은 Laravel 13, PHP 8.4, MySQL 8.4, Blade, Livewire, Tailwind CSS를 사용한다.
- 공식 Livewire Starter Kit의 세션 인증과 비밀번호 재설정 기능을 기반으로 한다.
- 서버에서 모든 권한을 다시 검사한다. 화면에서 버튼을 숨기는 것만으로 권한을 제한하지 않는다.
- 고객 계정은 한 고객사에만 소속하며, 요청, 댓글, 첨부파일, 견적, 시간 내역을 고객사 단위로 분리한다.
- 시간은 모두 정수 분 단위로 저장한다.
- 승인, 예약, 차감, 반환, 월 마감은 데이터베이스 트랜잭션으로 처리한다.
- 승인된 견적과 마감된 시간 기록은 덮어쓰지 않는다. 새 버전 또는 조정 원장을 추가한다.
- 파일은 비공개 저장소에 보관하고, 다운로드 직전에 사용자와 고객사 권한을 검사한다.
- 오래 걸리는 알림과 보고 작업은 데이터베이스 큐에서 실행하고, 정기 작업은 Scheduler에서 실행한다.
- 관리자 템플릿은 화면 구조와 디자인 기준으로 사용한다. React 애플리케이션을 함께 운영하지 않고 필요한 레이아웃, 색상, 간격, 아이콘과 화면 구성을 Blade와 Livewire로 옮긴다.

## 현재 구축 상태

현재 저장소에는 Laravel 13과 Livewire Starter Kit, PHP 8.4 실행 환경, MySQL 8.4, 데이터베이스 큐, Scheduler, 비공개 파일 저장소 설정이 준비되어 있다. 기본 로그인, 비밀번호 재설정, 프로필과 보안 설정 화면도 설치되어 있다. 고객사와 사용자 소속·역할, 초대 전용 가입 절차까지 구현되어 있다. 관리자 템플릿 원본은 `admin-template-source`에 보관되어 있다.

아직 프로젝트와 요청에 대한 고객사 범위 정책, 프로젝트와 요청, 견적 승인, 작업시간 원장, 월 마감, 첨부파일 업무 기능은 구현되지 않은 것으로 본다.

## 체크박스 운영 규칙

- `[ ]`는 아직 완료 조건을 충족하지 않은 항목이다.
- `[x]`는 구현, 자동 테스트, 관련 수동 확인이 모두 끝난 항목이다.
- 작업은 항목 번호 순서대로 진행한다. 앞 항목이 끝나지 않으면 뒤 항목을 완료 처리하지 않는다.
- 외부 정보나 별도 결정이 필요해 진행할 수 없으면 체크하지 않고 항목 아래에 막힌 이유를 기록한다.
- 기존 코드가 있어도 현재 저장소에서 다시 검증하기 전에는 완료로 보지 않는다.
- 체크할 때는 항목 아래에 확인한 파일이나 실행한 검증 명령을 근거로 남긴다.

현재 작업 위치는 1.4이다. 2026년 10월 2일 기준으로 0단계 전체와 1.1부터 1.3까지 구현하고 검증했다.

## 전체 개발 순서

| 단계 | 구현 범위 | 이 단계가 끝나면 가능한 일 |
| --- | --- | --- |
| 0 | 기반과 화면 기준 확정 | 팀이 같은 규칙과 화면 구조로 개발을 시작할 수 있다 |
| 1 | 인증, 고객사 분리, 프로젝트, 요청 | 고객이 자기 회사의 요청을 안전하게 등록하고 조회할 수 있다 |

## 0단계 기반과 화면 기준 확정

### 목표

개발 중에 데이터 구조, 권한 체계, 상태 이름과 화면 구성이 반복해서 바뀌지 않도록 공통 기준을 먼저 확정한다.

### 구현 목록

- [x] **0.1 로컬 실행 기준을 고정한다**
   - Docker Compose로 웹, MySQL, 큐 작업자, Scheduler를 함께 실행한다.
   - 애플리케이션 주소는 `http://localhost:8000`, 호스트의 MySQL 포트는 `3307`을 사용한다.
   - `.env.example`에는 실제 비밀번호나 운영 키를 넣지 않는다.
   - 신규 개발자가 README의 명령만으로 설치, 마이그레이션, 빌드, 테스트를 완료할 수 있게 유지한다.
   - 검증 근거: `docker compose ps`에서 `laravel.test`, `mysql`, `queue`, `scheduler`가 실행 중이고 MySQL 상태가 `healthy`임을 확인했다.

- [x] **0.2 코드 품질 명령을 기준선으로 정한다**
   - PHP 코딩 형식은 Pint로 검사한다.
   - 정적 분석은 PHPStan과 Larastan으로 실행한다.
   - 기능 검증은 PHPUnit 기반 Laravel 테스트로 실행한다.
   - 프런트 자원은 `npm run build`로 빌드한다.
   - 배포 전에는 위 네 가지 검사가 모두 성공해야 한다.
   - 검증 근거: Composer 잠금 파일 해시를 현재 `composer.json`과 맞췄고 `composer validate --strict`가 통과했다. 현재 기준 Pint 68개 파일, PHPStan 오류 0건, PHPUnit 64개 테스트와 208개 단언, 호스트의 프런트 빌드가 모두 성공했다.

- [x] **0.3 역할과 권한 이름을 코드로 확정한다**
   - 최고 관리자: 전체 설정과 모든 고객사 자료를 관리한다.
   - 운영자: 허용된 고객사, 계약, 견적, 작업, 시간과 월 마감을 관리한다.
   - 고객사 관리자: 자사 요청과 견적 승인, 검수 완료, 사용내역 조회를 수행한다.
   - 고객사 일반 사용자: 자사 요청 등록, 열람과 댓글 작성을 수행한다.
   - 초기 운영에서는 최고 관리자 한 명이 운영자 업무를 함께 수행한다.
   - 역할과 권한 이름은 PHP 열거형으로 정의하고 역할별 권한표를 단위 테스트로 고정한다.
   - 검증 근거: `app/Enums/UserRole.php`, `app/Enums/Permission.php`와 `tests/Unit/Enums/UserRoleTest.php`를 추가했고 역할 단위 테스트가 통과했다.

- [x] **0.4 요청 상태와 화면 용어를 코드로 확정한다**
   - 요청 기본 상태는 `접수`, `견적 중`, `승인 대기`, `작업 대기`, `진행 중`, `검수 대기`, `완료`로 한다.
   - `보류`와 `취소`는 별도 상태로 기록한다.
   - 반려와 수정 요청은 상태만 되돌리지 않고 사유, 처리자, 처리시각과 이전 상태를 함께 기록한다.
   - 데이터베이스에는 안정적인 영문 값을 저장하고 화면에는 한글 이름을 표시한다.
   - 상태 값과 한글 이름은 PHP 열거형으로 정의하고 단위 테스트로 고정한다. 상태 전환 규칙은 2.6에서 구현한다.
   - 검증 근거: `app/Enums/WorkRequestStatus.php`와 `tests/Unit/Enums/WorkRequestStatusTest.php`를 추가했다. 열거형 전체 검증은 7개 테스트, 48개 단언으로 통과했다.

- [x] **0.5 관리자 템플릿을 화면 설계 기준으로 정리한다**
   - 템플릿의 사이드바, 상단 영역, 목록, 카드, 표, 입력 화면과 상세 화면을 목록화한다.
   - Approid Desk에 필요한 구성만 골라 Blade 레이아웃과 Livewire 컴포넌트로 다시 만든다.
   - 템플릿 자산을 복사하기 전에 사용 권한과 라이선스를 확인한다.
   - 공통 색상, 글꼴 크기, 간격, 버튼, 배지와 표 스타일을 Tailwind 기준으로 한곳에 정리한다.
   - 검증 근거: `docs/admin-template-mapping.md`에 원본 구성, 역할별 메뉴, 화면 매핑, 색상 토큰, 공통 컴포넌트와 제외 범위를 정리했다. 별도 라이선스 파일이 없는 사실과 내부 사용 원칙도 기록했다.

- [x] **0.6 현재 구현 가능한 기본 보안 설정을 적용한다**
   - 운영 환경에서는 HTTPS, Secure 쿠키, HttpOnly 쿠키, SameSite 설정을 적용한다.
   - 운영 환경에서 `APP_DEBUG`를 끄고 오류 상세가 고객에게 노출되지 않게 한다.
   - 활동 기록에 비밀번호, 토큰, 세션 값과 원문 접속정보를 남기지 않는다.
   - 로그인과 비밀번호 재설정의 요청 횟수 제한을 확인한다.
   - 초대 수락 제한은 1.3에서, 파일 다운로드 제한은 4.6에서 해당 기능과 함께 구현한다.
   - 검증 근거: `SecurityHeaders` 미들웨어, 운영 환경의 Secure 쿠키 기본값, HttpOnly와 SameSite 설정, 로그인과 비밀번호 재설정 제한을 적용했다. 보안 기준 테스트 4개와 단언 17개가 통과했다.

### 완료 조건

- README만으로 전체 개발 환경을 다시 실행할 수 있다.
- 역할, 요청 상태와 상태 변경 규칙이 코드와 문서에서 같은 이름을 사용한다.
- 관리자 템플릿의 적용 대상 화면 목록과 공통 UI 기준이 정리되어 있다.
- 기본 테스트, 코드 형식 검사, 정적 분석과 프런트 빌드가 모두 성공한다.

## 1단계 인증 고객사 분리 프로젝트 요청

### 목표

초대받은 사용자가 로그인해 자기 고객사의 프로젝트와 요청만 등록하고 조회하도록 만든다. 다른 고객사의 URL이나 파일 식별자를 알아도 접근할 수 없어야 한다.

### 데이터 구현

- [x] **1.1 고객사 정보를 만든다**
   - `companies`에 회사명, 상태, 대표 연락처와 메모를 저장한다.
   - 삭제된 고객사의 과거 작업 이력을 보존하기 위해 운영 중인 고객사는 원칙적으로 물리 삭제하지 않고 비활성 처리한다.
   - 검증 근거: 고객사 마이그레이션, `CompanyStatus`, 모델과 팩토리를 추가했다. 고객사 테스트 3개와 단언 8개가 통과했고 개발 DB에 마이그레이션을 적용했다.

- [x] **1.2 사용자 소속과 역할을 추가한다**
   - 고객 계정에는 반드시 `company_id`와 고객 역할이 있어야 한다.
   - 최고 관리자와 운영자는 시스템 계정으로 구분하고 접근 가능한 고객사 범위를 별도 정책으로 판단한다.
   - 고객 사용자가 두 고객사에 동시에 소속되지 않도록 데이터베이스 제약과 저장 검증을 함께 둔다.
   - 검증 근거: 사용자에 `company_id`, 역할과 활성 상태를 추가했다. 시스템 역할은 고객사 없이, 고객 역할은 고객사와 함께 저장하도록 MySQL 제약을 적용했다. 공개 회원가입을 닫았고 관련 테스트 7개와 단언 13개가 통과했다.

- [x] **1.3 초대 데이터와 초대 수락 규칙을 만든다**
   - 관리자가 이메일, 고객사, 역할과 만료시각을 지정해 초대한다.
   - 초대 토큰은 원문을 저장하지 않고 해시로 저장한다.
   - 이미 사용했거나 만료된 초대는 다시 사용할 수 없다.
   - 회원가입 화면은 공개 가입이 아니라 유효한 초대에서만 접근하게 한다.
   - 검증 근거: 초대 마이그레이션, 모델, 생성·수락 액션, 수락 화면과 요청 제한을 구현했다. 토큰 원문 비저장, 시스템 역할 지정 차단, 만료·폐기·재사용·변조·비활성 고객사 차단과 재초대 검증을 포함한 초대 테스트 11개와 단언 44개가 통과했고 개발 DB에 마이그레이션을 적용했다. 실제 로컬 HTTP 요청에서도 유효한 초대 화면이 200 응답과 고객사·이메일을 표시하는지 확인했다.

- [x] **1.4 프로젝트를 만든다**
   - `projects`에 고객사, 프로젝트명, 설명, 상태, 사이트 주소와 기술 메모를 저장한다.
   - 기존 홈페이지 프로젝트는 소스와 데이터베이스 자료의 확보 여부를 표시한다.
   - 접속정보 원문은 프로젝트 일반 메모에 저장하지 않고 별도의 암호화된 보안 정보 영역에 저장한다.
   - 검증 근거: 프로젝트와 암호화된 프로젝트 보안정보 마이그레이션, `ProjectStatus`, 모델 관계와 팩토리를 구현했다. 프로젝트 단위 테스트 6개와 단언 23개, 전체 테스트 70개와 단언 231개가 통과했고 개발 DB 마이그레이션, Pint 76파일, PHPStan 54파일과 프런트 빌드를 확인했다.

- [x] **1.5 요청을 만든다**
   - `work_requests`에 고객사, 프로젝트, 등록자, 제목, 요구사항, 유형, 우선순위, 긴급 여부, 희망일, 접수경로와 상태를 저장한다.

- 고객사 관리자가 로그인해 프로젝트와 요청을 등록할 수 있다.
- 고객사 일반 사용자가 자사 요청과 댓글만 사용할 수 있다.
- 고객사 간 접근 차단 테스트가 모두 통과한다.

## 2단계 견적 승인 계약 확인 상태 변경 이력

### 목표

요청 분석부터 견적 승인, 계약 확인, 작업 시작과 고객 검수까지의 흐름을 시스템에서 통제한다. 승인된 내용을 바꾸지 않고 새 버전과 이력으로 남긴다.

### 데이터 구현

- [ ] **2.1 계약 정보를 만든다**
   - `service_contracts`에 고객사, 계약 유형, 시작일, 종료일, 상태와 서명 확인 정보를 저장한다.
   - 계약서 파일과 서명 확인일, 확인자를 연결한다.
   - 서명 확인 전에는 요청을 `작업 대기` 또는 `진행 중`으로 바꿀 수 없다.

- [ ] **2.2 가격 기준을 만든다**
   - 작업 종류, 난이도, 시간당 단가, 긴급 가산 기준과 적용기간을 관리한다.
   - 과거 견적을 재현할 수 있도록 견적에는 당시 적용한 단가와 판단 근거를 복사해 저장한다.
   - 턱없이 낮은 예산이나 불가능한 일정은 거절 또는 재협의 상태와 사유로 기록한다.

- [ ] **2.3 견적과 견적 버전을 만든다**
   - 하나의 요청에 여러 견적 버전을 둘 수 있게 한다.
   - 각 버전에 포함 범위, 제외 범위, 예상시간, 예정일, 사용 대상 월, 금액, 작성자와 작성시각을 저장한다.
   - 고객에게 제출한 버전은 수정하지 못하게 하고 변경이 필요하면 새 버전을 만든다.
   - 최신 버전과 승인된 버전을 각각 명확히 식별한다.

- [ ] **2.4 승인 기록을 만든다**
   - 승인자, 역할, 승인한 견적 버전, 승인시각, 접속 정보와 승인 문구를 기록한다.
   - 고객사 관리자만 견적을 승인할 수 있다.
   - 같은 승인 요청이 새로고침이나 재전송으로 두 번 처리되지 않도록 고유한 멱등성 키를 사용한다.

- [ ] **2.5 상태 변경 이력을 만든다**
   - 이전 상태, 새 상태, 변경자, 변경 사유, 관련 견적 버전과 발생시각을 저장한다.
   - 허용된 상태 전환을 서비스 계층 한곳에서 검사한다.
   - 반려, 수정 요청, 보류와 취소는 사유를 필수로 받는다.

### 상태 전환 규칙

| 현재 상태 | 가능한 다음 상태 | 필요한 조건 |
| --- | --- | --- |
| 접수 | 견적 중, 보류, 취소 | 운영자가 요청 내용을 확인한다 |
| 견적 중 | 승인 대기, 보류, 취소 | 제출 가능한 견적 버전이 있다 |
| 승인 대기 | 작업 대기, 견적 중, 취소 | 고객사 관리자가 최신 견적을 승인하면 작업 대기로 이동한다. 수정 요청이면 견적 중으로 돌아간다 |
| 작업 대기 | 진행 중, 보류, 취소 | 견적 승인과 계약서 서명 확인이 모두 끝났다 |
| 진행 중 | 검수 대기, 작업 대기, 보류, 취소 | 구현과 내부 검사가 끝나면 검수 대기로 이동한다. 추가 승인이 필요하면 작업 대기로 돌아간다 |
| 검수 대기 | 완료, 진행 중, 보류 | 고객이 승인하면 완료한다. 수정 요청이면 사유와 함께 진행 중으로 돌아간다 |
| 완료 | 진행 중 | 최초 합의 기능의 오류를 무상 수정하는 경우 새 수정 이력을 남기고 재개한다 |
| 보류 | 이전 작업 상태, 취소 | 재개 사유와 처리자를 기록한다 |
| 취소 | 없음 | 관리자만 별도 복구 절차로 새 요청을 만들 수 있다 |

### 트랜잭션과 동시성 처리

- [ ] **2.6 요청 상태 전환 서비스를 구현한다**
  - 허용된 상태와 역할을 한곳에서 검사한다.
  - 상태 변경에 실패하면 일부 이력만 저장되지 않도록 전체 작업을 되돌린다.
- [ ] **2.7 견적 승인 트랜잭션을 구현한다**
  - 승인 기록 생성, 견적 버전 고정과 요청 상태 변경을 하나의 트랜잭션으로 처리한다.
  - 이미 승인된 견적 버전에는 두 번째 승인 기록을 만들지 않는다.
- [ ] **2.8 견적 승인 동시성 제어를 구현한다**
  - 대상 견적과 월 계약시간 행을 잠가 동시에 승인되는 요청도 안전하게 계산한다.

### 화면 구현

- [ ] **2.9 요청 상세에 견적과 승인 이력을 표시한다**
  - 분석 내용, 견적 버전, 계약 확인, 상태 이력과 고객 승인을 시간순으로 표시한다.
- [ ] **2.10 운영자 견적 작성 화면을 만든다**
  - 가격 기준을 참고해 작성하고 미리보기한 뒤 제출한다.
- [ ] **2.11 고객 견적 승인 화면을 만든다**
  - 포함 범위, 제외 범위, 예상시간, 금액, 예정일과 사용 대상 월을 확인하고 승인 또는 수정 요청한다.
- [ ] **2.12 역할과 상태에 맞는 작업 버튼을 구현한다**
  - 화면 표시와 서버 권한 검사가 같은 규칙을 사용한다.
- [ ] **2.13 운영 대시보드에 승인과 검수 대기 현황을 표시한다**

### 필수 테스트

- 고객사 일반 사용자의 견적 승인 요청을 거부하는지 검사한다.
- 다른 고객사의 관리자가 견적을 승인할 수 없는지 검사한다.
- 같은 승인 요청을 두 번 보내도 승인과 상태 변경이 한 번만 반영되는지 검사한다.
- 제출 또는 승인된 견적을 직접 수정할 수 없는지 검사한다.
- 견적 변경 시 새 버전이 생성되고 다시 승인받는지 검사한다.
- 계약서 서명 확인 전에는 작업을 시작할 수 없는지 검사한다.
- 반려, 수정 요청, 보류와 취소에 사유가 남는지 검사한다.

### 완료 조건

- 견적 작성, 고객 승인, 계약 확인, 작업 시작과 검수 완료를 한 요청 안에서 처리할 수 있다.
- 승인된 견적은 고정되고 모든 변경은 새 버전으로 남는다.
- 허용되지 않은 역할과 상태 전환이 서버에서 차단된다.
- 중복 승인과 동시 승인 테스트가 통과한다.

## 3단계 작업시간 시간 원장 월 정산

### 목표

월 제공시간, 승인된 예상시간, 실제 작업시간과 반환시간을 원장으로 관리한다. 동시 승인과 재전송이 있어도 사용 가능시간이 음수가 되거나 이중 차감되지 않게 한다.

### 시간 계산 원칙

`사용 가능시간 = 월 제공시간 - 실사용시간 - 남은 예약시간`

예를 들어 월 제공시간이 1,200분이고 180분 견적을 승인하면 180분을 예약한다. 실제 작업 150분을 확정하면 예약 150분을 실사용 150분으로 전환한다. 요청 완료 시 남은 예약 30분을 반환하므로 최종 사용 가능시간은 1,050분이다.

### 데이터 구현

- [ ] **3.1 월 계약시간을 만든다**
   - `contract_months`에 계약, 기준 연월, 제공 분, 상태, 마감시각과 마감자를 저장한다.
   - 같은 계약과 연월 조합은 한 행만 존재하게 한다.
   - 미사용 시간은 다음 달로 이월하지 않는다.

- [ ] **3.2 변경 불가능한 시간 원장을 만든다**
   - `time_ledger_entries`에 고객사, 계약 월, 요청, 발생 종류, 분, 원인 자료, 처리자, 사유와 발생시각을 저장한다.
   - 발생 종류는 제공, 예약, 예약 해제, 실사용, 사용 취소, 조정 증가, 조정 감소로 구분한다.
   - 원장 행은 수정하거나 삭제하지 않고, 잘못된 기록은 반대 방향의 조정 행으로 정정한다.
   - 원인 자료와 발생 종류 조합에 고유 제약을 두어 같은 사건이 두 번 반영되지 않게 한다.

- [ ] **3.3 작업기록을 만든다**
   - `work_logs`에 요청, 작업자, 작업일, 작업 내용, 소요 분, 차감 여부, 상태와 확정시각을 저장한다.
   - 임시저장 작업기록은 시간에 반영하지 않고 확정된 기록만 실사용시간에 반영한다.
   - 개발자 귀책 수정은 `고객 차감 안 함`으로 표시하고 사유를 필수로 남긴다.

- [ ] **3.4 월 마감과 조정을 만든다**
   - 마감 시 제공, 예약, 실사용, 반환과 조정 합계를 계산해 마감 결과를 저장한다.
   - 마감 후 원본 작업기록과 원장을 직접 바꾸지 못하게 한다.
   - 마감 후 오류는 조정 사유, 승인자와 관련 원장을 가진 조정 이력으로 정정한다.

### 처리 규칙

- [ ] **3.5 견적 승인 시 예상시간을 예약한다**
   - 승인할 월의 제공, 사용, 예약 합계를 행 잠금 상태에서 다시 계산한다.
   - 예상시간을 예약하고 사용 가능시간이 부족하면 승인을 중단한다.
   - 견적 승인과 예약 원장 생성은 같은 트랜잭션에서 처리한다.

- [ ] **3.6 작업시간 확정 시 예약을 실사용으로 전환한다**
   - 확정할 작업시간만큼 예약을 줄이고 같은 분을 실사용으로 늘린다.
   - 같은 작업기록을 다시 확정해도 원장이 한 번만 생성되어야 한다.
   - 남은 예약보다 많은 시간을 확정하려면 추가 견적 승인을 먼저 받는다.

- [ ] **3.7 완료와 취소 시 남은 예약을 해제한다**
   - 사용하지 않은 예약시간을 모두 해제한다.
   - 이미 확정된 실사용시간은 자동으로 되돌리지 않는다.
   - 실사용 취소가 필요하면 사유가 있는 별도 원장을 만든다.

- [ ] **3.8 견적 변경 시 기존 예약을 교체한다**
   - 기존 승인 견적의 남은 예약을 먼저 해제한다.
   - 새 견적 버전을 승인할 때 새 예상시간을 예약한다.
   - 두 동작은 이력과 원장을 통해 각각 추적할 수 있어야 한다.

- [ ] **3.9 월 전환 절차를 구현한다**
   - 월말까지 사용하지 않은 예약은 기존 월에서 해제한다.
   - 다음 달에 계속할 작업은 다음 달 사용분을 새 견적으로 승인받는다.
   - Scheduler는 월 전환 대상만 찾아 알리고, 승인 없이 자동으로 다음 달 시간을 차감하지 않는다.

- [ ] **3.10 무상 수정 시간을 별도로 기록한다**
   - 작업시간은 그대로 기록한다.
   - 고객 차감 여부를 끄고 귀책 사유를 남긴다.
   - 운영 보고에는 전체 투입시간과 고객 차감시간을 구분한다.

### 화면 구현

- [ ] **3.11 운영 대시보드에 고객별 시간 현황을 표시한다**
- [ ] **3.12 고객 대시보드에 자사 시간 현황을 표시한다**
- [ ] **3.13 작업시간 입력 화면을 만든다**
- [ ] **3.14 월 사용내역과 원장 화면을 만든다**
- [ ] **3.15 운영자 월 마감과 조정 화면을 만든다**
- [ ] **3.16 권한을 검사하는 월 사용내역 CSV 다운로드를 만든다**

### 필수 테스트

- 동시에 두 견적을 승인해도 남은 시간보다 많이 예약되지 않는지 검사한다.
- 같은 승인 요청과 같은 작업기록 확정이 두 번 반영되지 않는지 검사한다.
- 완료와 취소 시 남은 예약만 반환되는지 검사한다.
- 견적 변경 시 이전 예약이 해제되고 새 예약이 생성되는지 검사한다.
- 승인시간을 넘는 작업기록이 추가 승인 없이 확정되지 않는지 검사한다.
- 무상 수정 작업이 기록에는 포함되지만 고객 사용시간에서는 제외되는지 검사한다.
- 월 전환 시 기존 예약이 해제되고 다음 달 승인 전에는 차감되지 않는지 검사한다.
- 마감된 월의 기록을 직접 수정할 수 없고 조정 이력으로만 정정되는지 검사한다.
- 고객사 A가 고객사 B의 월 내역과 CSV를 내려받을 수 없는지 검사한다.

### 완료 조건

- 예시 계산과 화면의 제공, 사용, 예약, 사용 가능시간이 일치한다.
- 모든 시간 변화가 원인 자료와 함께 원장에 남는다.
- 동시 처리와 재전송 상황에서도 초과 예약과 이중 차감이 발생하지 않는다.
- 마감 후 변경은 조정 이력으로만 처리된다.

## 4단계 첨부파일 알림 자동화 데모 배포

### 목표

업무에 필요한 자료와 알림을 안전하게 운영하고, 핵심 시나리오와 복구 절차를 검증한 뒤 서비스를 배포한다.

### 첨부파일 구현

- [ ] **4.1 첨부파일 데이터와 업무 자료 연결을 구현한다**
- [ ] **4.2 첨부파일의 이름 크기 유형 업로더 고객사 검사 상태를 저장한다**
- [ ] **4.3 실제 파일 유형과 허용 목록을 검사한다**

### 운영 승인 전 최종 검사

- 다른 고객사의 요청, 댓글, 견적, 시간 내역, CSV와 파일에 접근할 수 없다.
- 고객사 일반 사용자는 견적 승인, 검수 완료, 월 마감과 조정을 수행할 수 없다.
- 동시 승인으로 사용 가능시간보다 많이 예약되지 않는다.
- 작업시간 재전송으로 이중 차감되지 않는다.
- 취소, 견적 변경, 무상 수정과 월 전환 계산이 모두 자동 테스트를 통과한다.
- 허용되지 않은 파일과 제한 용량을 넘는 파일이 차단된다.
- 알림 실패를 확인하고 안전하게 재시도할 수 있다.
- 데이터베이스와 첨부파일 백업을 실제로 복원할 수 있다.
- 운영 환경에서 디버그 정보와 비밀값이 노출되지 않는다.
- 데모 시나리오 전체를 수동으로 끝까지 실행할 수 있다.

### 완료 조건

- 자동 테스트, 코드 형식 검사, 정적 분석과 프런트 빌드가 모두 성공한다.
- 세 역할의 핵심 업무 흐름을 실제 브라우저에서 수동 확인했다.
- 데모 시나리오와 고객사 간 접근 차단 시연이 성공한다.
- 큐, Scheduler, 백업, 복원과 롤백 절차를 운영 환경과 같은 조건에서 검증했다.
- 배포 체크리스트, 장애 대응 기록 양식과 운영 인수 자료가 준비되어 있다.

## 개발 작업 우선순위

같은 단계 안에서는 다음 순서로 작업한다.

1. 데이터베이스 구조와 제약조건
2. 모델 관계와 상태 값
3. 정책과 서버 권한 검사
4. 업무 규칙을 처리하는 서비스와 트랜잭션
5. Livewire 화면과 입력 검증
6. 활동 이력과 알림
7. 자동 테스트
8. 실제 브라우저 수동 확인

화면부터 만든 뒤 권한이나 거래 규칙을 나중에 붙이지 않는다. 각 기능은 데이터 제약, 서버 권한, 업무 처리, 화면, 테스트가 한 묶음으로 끝나야 완료로 본다.

## 구현 중 지켜야 할 결정 규칙

- 요구사항이 기존 합의 범위를 벗어나면 원 요청을 수정하지 않고 연결된 새 요청과 새 견적으로 처리한다.
- 승인된 견적을 바꿔야 하면 새 견적 버전을 만들고 다시 승인받는다.
- 예산과 일정이 현실적으로 불가능하면 무리하게 진행하지 않고 가능한 범위와 일정을 다시 제안한다.
- 고객의 새 요구, 외부 서비스 변경, 고객 환경 변경은 기본적으로 유상 작업으로 본다.
- 최초 합의한 기능이 다르게 작동하면 무상 수정 후보로 기록하고 관리자와 개발자가 원인을 확인한다.
- 주요 업무 장애는 일반 요청보다 먼저 처리하고 1시간 안에 최초 응답한다.
- 여러 일반 요청은 긴급도, 접수 순서, 납기일 순서로 처리한다.
- 확인하지 않은 완료일과 복구시간을 고객에게 약속하지 않는다.
- 버그나 일정 지연 위험이 생기면 영향과 대응 계획을 먼저 정리하고 예정일 전에 고객과 협의한다.

## 전체 구현 완료의 정의

Approid Desk의 첫 운영 버전은 다음 조건을 모두 만족할 때 완료로 본다.

1. 요청 접수부터 견적, 승인, 계약 확인, 개발, 검수와 완료까지 한 시스템에서 처리할 수 있다.
2. 고객사별 데이터가 서버 권한과 데이터베이스 관계를 통해 분리되어 있다.
3. 제공시간, 예약시간, 실사용시간과 반환시간을 분 단위 원장으로 재현할 수 있다.
4. 승인된 견적과 마감된 시간은 덮어쓰지 않고 변경 이력으로 남는다.
5. 댓글, 파일, 작업기록, 승인, 상태 변경과 고객 확인 자료가 요청에 연결되어 있다.
6. 자동 테스트와 수동 검수가 끝났으며 실제 업무를 막는 장애가 없다.
7. 알림 재시도, 백업, 복원과 롤백이 검증되어 있다.
8. 데모 시나리오와 고객사 간 접근 차단을 반복해서 시연할 수 있다.
