# Approid Desk 개발 구현 순서

## 문서 목적

이 문서는 고객사의 신규 개발과 유지보수 요청을 접수하고, 견적과 승인, 개발, 검수, 시간 정산, 완료까지 관리하는 Approid Desk의 구현 순서를 정의한다. 각 단계는 앞 단계의 데이터와 권한 규칙을 전제로 하므로 아래 순서대로 개발한다. 각 단계의 완료 조건을 충족하기 전에는 다음 단계의 핵심 기능을 운영 환경에 배포하지 않는다.

## 개발 기준

- 기술 구성은 Laravel 13, PHP 8.4, MySQL 8.4, Blade, Livewire, Tailwind CSS를 사용한다.
- 공식 Livewire Starter Kit의 세션 인증과 비밀번호 재설정 기능을 기반으로 한다.
- 서버에서 모든 권한을 다시 검사한다. 화면에서 버튼을 숨기는 것만으로 권한을 제한하지 않는다.
- 고객 계정은 한 고객사에만 소속하며, 요청, 댓글, 첨부파일, 견적, 시간 내역을 고객사 단위로 분리한다.
- 시간은 모두 정수 분 단위로 저장한다.
- 승인, 예약, 차감, 반환, 월 마감은 데이터베이스 트랜잭션으로 처리한다.
- 승인된 견적과 마감된 시간 기록은 덮어쓰지 않는다. 새 버전 또는 조정 원장을 추가한다.
- 파일은 비공개 저장소에 보관하고, 다운로드 직전에 사용자와 고객사 권한을 검사한다.
- 오래 걸리는 알림과 보고 작업은 데이터베이스 큐에서 실행하고, 정기 작업은 Scheduler에서 실행한다.
- 관리자 템플릿은 화면 구조와 디자인 기준으로 사용한다. React 애플리케이션을 함께 운영하지 않고 필요한 레이아웃, 색상, 간격, 아이콘과 화면 구성을 Blade와 Livewire로 옮긴다.

## 현재 구축 상태

현재 저장소에는 Laravel 13과 Livewire Starter Kit, PHP 8.4 실행 환경, MySQL 8.4, 데이터베이스 큐, Scheduler, 비공개 파일 저장소 설정이 준비되어 있다. 기본 로그인, 비밀번호 재설정, 프로필과 보안 설정 화면도 설치되어 있다. 고객사와 사용자 소속·역할, 초대 전용 가입 절차까지 구현되어 있다. 관리자 템플릿 원본은 `admin-template-source`에 보관되어 있다.

고객사 범위 정책, 프로젝트·요청, 견적 버전·승인과 상태 전환 서비스, 월 계약시간·불변 시간 원장·승인 시 예약 및 동시성 제어, 요청 상세의 견적·승인 이력 조회, 운영자 견적 작성·미리보기·제출과 고객 승인·수정 요청 화면, 현재 지원하는 흐름의 역할·상태별 작업 버튼과 운영 승인·검수 대기·고객별 시간 현황 대시보드, 고객 대시보드의 자사 계약별 시간 현황, 작업기록 데이터 구조·임시저장·차감/비차감 시간 확정, 완료·취소 시 잔여 예약 반환, 사유 기반 실사용 취소, 재견적 예약 교체, 월 전환 및 월 마감·조정 처리가 구현되어 있으며 완료 항목별 검증 근거는 아래에 기록한다. 작업시간 입력·확정 화면, 월 사용내역·원장·마감 관리 화면과 권한을 검사하는 CSV 다운로드도 구현했다. 첨부파일은 요청·댓글·견적 버전 연결, 파일 정보·유형·용량·개수 검사, 임의 이름 비공개 저장, 권한·횟수 제한 다운로드, 삭제 상태·불변 처리 이력, ClamAV 악성 파일 검사와 논리적 격리까지 추가했으며 HTTP 업로드·목록·삭제 화면은 후속 항목에 남아 있다. 업무 알림은 19개 타입과 수신 그룹·중요도·기본 채널·보안 규칙, 공통 DB·큐 메일 발송, 재시도 정책과 사건별 중복 방지까지 구현했다.

## 체크박스 운영 규칙

- `[ ]`는 아직 완료 조건을 충족하지 않은 항목이다.
- `[x]`는 구현, 자동 테스트, 관련 수동 확인이 모두 끝난 항목이다.
- 작업은 원칙적으로 항목 번호 순서대로 진행한다. 선행 의존성 때문에 순서를 변경할 때는 사용자 승인과 변경 순서를 아래에 기록하고, 해당 항목을 실제 검증한 뒤 완료 처리한다.
- 외부 정보나 별도 결정이 필요해 진행할 수 없으면 체크하지 않고 항목 아래에 막힌 이유를 기록한다.
- 기존 코드가 있어도 현재 저장소에서 다시 검증하기 전에는 완료로 보지 않는다.
- 체크할 때는 항목 아래에 확인한 파일이나 실행한 검증 명령을 근거로 남긴다.

다음 작업 위치는 4.36 운영 환경 설정 재검증이다. 2026년 10월 4일 기준으로 0단계, 1단계 전체와 2.1~2.13, 3.1~3.16, 4.1~4.35를 완료했다(3.5는 승인된 선행 작업). 검수 완료와 승인 후 취소가 3.7의 원자적 잔여 예약 반환에 연결되어 2단계의 전체 업무 흐름 완료 조건도 충족했다.

2026-10-04 초기 운영 배포: 사용자 지시로 남은 4단계 항목보다 먼저 홈서버에 초기 빈 데이터베이스 배포를 진행했다. `https://desk.approid.team`을 Cloudflare Tunnel로 연결하고 앱·MySQL·ClamAV·터널, nginx·PHP-FPM·Queue·Scheduler 실행과 전체 운영 마이그레이션 적용을 확인했다. 초기 최고 관리자 1명이 활성·이메일 인증 상태로 생성되었고 Mailcow SMTP가 수락한 합성 확인 메일이 실제 받은편지함에 도착했음을 사용자가 확인했다. 공개 `/up`과 `/login`은 유효한 TLS로 HTTP 200을 반환했으며, 실제 Chromium의 1440px·375px 로그인 화면에서 가로 넘침과 콘솔 오류가 없었다. 이 기록은 초기 서비스 기동 확인이며 4.14 이후 기능, 재부팅 자동 복구, 백업·복원, 롤백과 운영 승인 완료를 뜻하지 않는다. 배포·비밀값 설정과 갱신 절차는 `docs/deployment.md`에 기록한다.

2026-10-03 HUD 셸 보완: Starter Kit의 사이드바 전용 레이아웃에 머물러 데스크톱 헤더가 연결되지 않은 원인을 확인하고, 원본 구조에 맞는 공통 헤더·접기·테마·역할별 메뉴·모바일 서랍을 적용했다. WSL 이동 중 유실은 아니며 최초 변경 시점은 Git 기록으로 특정할 수 없다. 실제 Chromium에서 86개 화면·폭·테마 조합과 8개 조작 검증 그룹을 통과했고, 원본과 대표 캡처를 직접 비교했다. 2.9~2.11의 기존 브라우저 확인 제한은 당시 기록으로 남기되 해당 화면은 이번 검사에 포함했다. 상세 근거와 재현 명령은 `docs/admin-template-mapping.md`에 기록한다. 이 검증은 모든 업무 시나리오의 수동 검수나 운영 배포 완료를 의미하지 않는다.

HUD 셸 복구 당시 최종 검사: 전체 PHPUnit **322개·1,345단언 통과**, 별도 Chromium 테스트 **1개·4단언 통과**(내부 86개 화면 조합·8개 조작 그룹), Pint **172파일 통과**, PHPStan **오류 0건**, 프런트 빌드 **22모듈 성공**, `git diff --check` 통과, 개발 `/up` HTTP 200. 공통 셸 검증 관문을 통과한 뒤 사용자 지시로 2.12를 진행했다. 운영 배포와 운영 DB 변경은 수행하지 않았다.

2026-10-03 사용자 승인으로 2.8의 선행 의존성을 먼저 구현했다: **3.1 월 계약시간 → 3.2 불변 시간 원장 → 3.5 승인 시 예약 → 2.8 동시성 검증 → 2.9 화면**. 전체 276개 테스트·962단언, Pint 163파일, PHPStan 오류 0건, 빌드 22모듈을 확인했다. 개발 DB에 `2026_10_03_060000_create_contract_time_tables`를 배치 13으로 적용하고 `/up` HTTP 200을 확인했다. 운영 배포 및 운영 DB 변경은 이번 작업에 포함하지 않았다.

## 0단계 기반과 화면 기준 확정

### 목표

개발 중에 데이터 구조, 권한 체계, 상태 이름과 화면 구성이 반복해서 바뀌지 않도록 공통 기준을 먼저 확정한다.

### 구현 목록

- [x] **0.1 로컬 실행 기준을 고정한다**
   - Docker Compose로 웹, MySQL, 큐 작업자, Scheduler를 함께 실행한다.
   - 애플리케이션 주소는 `http://localhost:8000`, 호스트의 MySQL 포트는 `3307`을 사용한다.
   - `.env.example`에는 실제 비밀번호나 운영 키를 넣지 않는다.
   - 신규 개발자가 README의 명령만으로 설치, 마이그레이션, 빌드, 테스트를 완료할 수 있게 유지한다.
   - 검증 근거: `docker compose ps`에서 `laravel.test`, `mysql`, `queue`, `scheduler`가 실행 중이고 MySQL 상태가 `healthy`임을 확인했다.

- [x] **0.2 코드 품질 명령을 기준선으로 정한다**
   - PHP 코딩 형식은 Pint로 검사한다.
   - 정적 분석은 PHPStan과 Larastan으로 실행한다.
   - 기능 검증은 PHPUnit 기반 Laravel 테스트로 실행한다.
   - 프런트 자원은 `npm run build`로 빌드한다.
   - 배포 전에는 위 네 가지 검사가 모두 성공해야 한다.
   - 검증 근거: Composer 잠금 파일 해시를 현재 `composer.json`과 맞췄고 `composer validate --strict`가 통과했다. 현재 기준 Pint 68개 파일, PHPStan 오류 0건, PHPUnit 64개 테스트와 208개 단언, 호스트의 프런트 빌드가 모두 성공했다.

- [x] **0.3 역할과 권한 이름을 코드로 확정한다**
   - 최고 관리자: 전체 설정과 모든 고객사 자료를 관리한다.
   - 운영자: 허용된 고객사, 계약, 견적, 작업, 시간과 월 마감을 관리한다.
   - 고객사 관리자: 자사 요청과 견적 승인, 검수 완료, 사용내역 조회를 수행한다.
   - 고객사 일반 사용자: 자사 요청 등록, 열람과 댓글 작성을 수행한다.
   - 초기 운영에서는 최고 관리자 한 명이 운영자 업무를 함께 수행한다.
   - 역할과 권한 이름은 PHP 열거형으로 정의하고 역할별 권한표를 단위 테스트로 고정한다.
   - 검증 근거: `app/Enums/UserRole.php`, `app/Enums/Permission.php`와 `tests/Unit/Enums/UserRoleTest.php`를 추가했고 역할 단위 테스트가 통과했다.

- [x] **0.4 요청 상태와 화면 용어를 코드로 확정한다**
   - 요청 기본 상태는 `접수`, `견적 중`, `승인 대기`, `작업 대기`, `진행 중`, `검수 대기`, `완료`로 한다.
   - `보류`와 `취소`는 별도 상태로 기록한다.
   - 반려와 수정 요청은 상태만 되돌리지 않고 사유, 처리자, 처리시각과 이전 상태를 함께 기록한다.
   - 데이터베이스에는 안정적인 영문 값을 저장하고 화면에는 한글 이름을 표시한다.
   - 상태 값과 한글 이름은 PHP 열거형으로 정의하고 단위 테스트로 고정한다. 상태 전환 규칙은 2.6에서 구현한다.
   - 검증 근거: `app/Enums/WorkRequestStatus.php`와 `tests/Unit/Enums/WorkRequestStatusTest.php`를 추가했다. 열거형 전체 검증은 7개 테스트, 48개 단언으로 통과했다.

- [x] **0.5 관리자 템플릿을 화면 설계 기준으로 정리한다**
   - 템플릿의 사이드바, 상단 영역, 목록, 카드, 표, 입력 화면과 상세 화면을 목록화한다.
   - Approid Desk에 필요한 구성만 골라 Blade 레이아웃과 Livewire 컴포넌트로 다시 만든다.
   - 템플릿 자산을 복사하기 전에 사용 권한과 라이선스를 확인한다.
   - 공통 색상, 글꼴 크기, 간격, 버튼, 배지와 표 스타일을 Tailwind 기준으로 한곳에 정리한다.
   - 검증 근거: `docs/admin-template-mapping.md`에 원본 구성, 역할별 메뉴, 화면 매핑, 색상 토큰, 공통 컴포넌트와 제외 범위를 정리했다. 별도 라이선스 파일이 없는 사실과 내부 사용 원칙도 기록했다.

- [x] **0.6 현재 구현 가능한 기본 보안 설정을 적용한다**
   - 운영 환경에서는 HTTPS, Secure 쿠키, HttpOnly 쿠키, SameSite 설정을 적용한다.
   - 운영 환경에서 `APP_DEBUG`를 끄고 오류 상세가 고객에게 노출되지 않게 한다.
   - 활동 기록에 비밀번호, 토큰, 세션 값과 원문 접속정보를 남기지 않는다.
   - 로그인과 비밀번호 재설정의 요청 횟수 제한을 확인한다.

| 진행 중 | 검수 대기, 승인 대기, 작업 대기, 보류, 취소 | 구현과 내부 검사가 끝나면 검수 대기로 이동한다. 새 견적 제출은 승인 대기로 이동하며 승인되면 작업 대기로 돌아간다 |
| 검수 대기 | 완료, 진행 중, 보류 | 고객이 승인하면 완료한다. 수정 요청이면 사유와 함께 진행 중으로 돌아간다 |
| 완료 | 진행 중 | 최초 합의 기능의 오류를 무상 수정하는 경우 새 수정 이력을 남기고 재개한다 |
| 보류 | 이전 작업 상태, 취소 | 재개 사유와 처리자를 기록한다 |
| 취소 | 없음 | 관리자만 별도 복구 절차로 새 요청을 만들 수 있다 |

### 트랜잭션과 동시성 처리

- [x] **2.6 요청 상태 전환 서비스를 구현한다**
  - 허용된 상태와 역할을 한곳에서 검사한다.
  - 상태 변경에 실패하면 일부 이력만 저장되지 않도록 전체 작업을 되돌린다.
  - 검증 근거: `TransitionWorkRequest`에서 요청·처리자를 잠그고 역할과 고객사 범위, 최신 제출/승인 견적, 유효한 서명 계약, 고객 검수, 사유와 무상 수정 조건을 검사한다. 상태·상세 이력·화면용 활동을 같은 트랜잭션으로 저장하며 활동 저장 실패 시 모두 롤백되는지 테스트했다. 일반 모델의 직접 상태 변경은 Observer에서 차단하고 기존 관련 테스트도 서비스 경로로 전환했다. 승인과 상태 변경의 결합은 2.7, 시간 예약은 3.5에서 연결하며 아직 외부 상태 변경 라우트는 열지 않는다. 직접 SQL 또는 `saveQuietly`는 내부 전용이므로 일반 업무 코드에서 사용하지 않는다.
- [x] **2.7 견적 승인 트랜잭션을 구현한다**
  - 승인 기록 생성, 견적 버전 고정과 요청 상태 변경을 하나의 트랜잭션으로 처리한다.
  - 이미 승인된 견적 버전에는 두 번째 승인 기록을 만들지 않는다.
  - 검증 근거(2026-10-03): `ApproveEstimateVersion` 안에서 승인 기록·승인 버전 참조 저장과 `TransitionWorkRequest`의 작업 대기 전환을 같은 트랜잭션으로 연결했다. 신규 승인은 승인 대기 상태에서만 가능하며, 제출본의 기존 DB 불변성 제약은 유지한다. 계약 서명 미확인, 상태 이력 저장 실패, 상태 변경 활동 저장 실패 시 승인·참조·상태·추가 이력이 모두 롤백되는지 검증했다. 같은 키 재전송은 원래 결과를 반환하고 새 이력을 만들지 않으며 다른 키로 동일 버전을 다시 승인할 수 없다. 승인·전환 관련 44개 테스트·113단언, 전체 247개·841단언, Pint 151파일, PHPStan 오류 0건, 빌드 22모듈이 통과했다. 새 DB 구조 변경은 없으며 `migrate`는 `Nothing to migrate`를 확인했다. 월 시간 예약은 3.5에서 같은 트랜잭션에 연결하고 외부 승인 경로는 그 전까지 열지 않는다.
- [x] **2.8 견적 승인 동시성 제어를 구현한다**
  - 대상 견적과 월 계약시간 행을 잠가 동시에 승인되는 요청도 안전하게 계산한다.
  - 선행 의존성: 3.1·3.2·3.5. 서로 다른 고객사 관리자가 같은 월의 서로 다른 요청을 동시에 승인하는 경우도 검증한다.
  - 검증 근거(2026-10-03): `ApprovalConcurrencyTest`에서 독립 PHP 프로세스 2개와 실제 MySQL 연결을 사용해 4가지 경쟁 상황을 통과했다. 같은 월 100분에 각각 60분인 요청 2개는 하나만 승인되고, 120분이면 둘 다 승인된다. 같은 키 재전송은 동일 승인 ID를 반환하고 다른 키 중복 승인은 거부된다. 부모 연결이 대상 행을 잠근 동안 두 작업 프로세스가 잠금 쿼리에 도달했음을 확인한 후 잠금을 해제하며 승인·예약·상태 이력 수와 잔액을 검사한다. 원장 조회도 `FOR UPDATE`를 사용해 REPEATABLE READ의 오래된 스냅샷으로 계산하지 않는다. 데드락은 전체 승인 트랜잭션 단위로 최대 5회 시도한다.
  - 테스트 정리 과정에서 발견한 기존 견적 마이그레이션의 롤백 오류도 수정했다. InnoDB가 외래키 인덱스를 더 넓은 고유 인덱스로 대체한 경우, 외래키 지원 인덱스를 복원한 뒤 고유 인덱스를 삭제한다. `DatabaseMigrations`의 생성·롤백을 포함한 전체 테스트가 통과했다.

## 3단계 작업시간 시간 원장 월 정산

### 목표

월 제공시간, 승인된 예상시간, 실제 작업시간과 반환시간을 원장으로 관리한다. 동시 승인과 재전송이 있어도 사용 가능시간이 음수가 되거나 이중 차감되지 않게 한다.

### 시간 계산 원칙

`사용 가능시간 = 월 제공시간 - 실사용시간 - 남은 예약시간`

예를 들어 월 제공시간이 1,200분이고 180분 견적을 승인하면 180분을 예약한다. 실제 작업 150분을 확정하면 예약 150분을 실사용 150분으로 전환한다. 요청 완료 시 남은 예약 30분을 반환하므로 최종 사용 가능시간은 1,050분이다.

   - DB는 마감·조정 기록 수정/삭제, 마감된 월의 일반 원장 추가, 승인 조정 기록과 일치하지 않는 조정 원장을 차단한다. 작업기록은 요청의 계약과 작업일 월을 기준으로 기존/새 월 모두 검사하며 마감된 월의 생성·수정·삭제는 직접 SQL도 차단한다. `SaveWorkLogDraft`도 월 행 잠금 아래 같은 제한을 확인한다. 미확정 작업기록과 예약이 있는 월은 3.6·3.7 처리 전까지 마감할 수 없고 이를 자동 삭제하거나 반환하지 않는다. 관리 화면은 3.15에 남겨 둔다.
   - 서버 검증(2026-10-03): 신규 25개 테스트에서 정확한 합계·마감 재전송·권한·관련 원장 범위·음수 잔액·미확정 기록/예약 차단·마감 후 SQL 우회 차단·조정 불변성·실패 롤백을 확인했다. 별도 DB 연결의 동시 마감·조정 잔액 경쟁·같은 키 재전송·마감 대 조정·마감 대 초안 저장 5개 시나리오도 통과했다. MySQL의 외래키 보조 인덱스 대체로 발생한 롤백 오류를 수정하고 재검증했다. 전체 **426개 테스트·2,666단언 통과**, Pint **194파일 통과**, PHPStan **오류 0건**, 빌드 **22모듈 성공**. 개발 DB 마이그레이션 `2026_10_03_080000_create_month_closures_and_adjustments`를 **배치 15**로 적용했다. 실제 고객사의 월을 마감/조정하거나 운영 DB를 변경하지 않았다.

### 처리 규칙

- [x] **3.5 견적 승인 시 예상시간을 예약한다**
   - 승인할 월의 제공, 사용, 예약 합계를 행 잠금 상태에서 다시 계산한다.
   - 예상시간을 예약하고 사용 가능시간이 부족하면 승인을 중단한다.
   - 견적 승인과 예약 원장 생성은 같은 트랜잭션에서 처리한다.
   - 월 계약시간이 없거나 마감됐거나 잔여시간이 부족하면 승인·상태·이력·예약을 모두 롤백한다. 미사용 시간은 다른 월에서 가져오지 않는다.
   - 최초 승인과 재견적 승인을 구분한다. 최초 승인은 기존 원장을 자동 반환하지 않고 현재 가용시간을 그대로 검사하며, 이미 승인 버전이 있는 요청의 신규 승인은 3.8의 기존 예약 교체를 사용한다. 기존 승인 키 재전송은 원래 결과를 반환한다.
   - 검증 근거(2026-10-03): `ApproveEstimateVersion` 내부에서 `ReserveEstimateTime`을 호출해 해당 계약/월 행을 잠그고 원장 잔액을 다시 계산한 뒤 승인 원인 예약을 추가한다. 예약·승인·버전 참조·상태·상세 이력·활동은 같은 트랜잭션에 포함한다. `ContractTimeTest`, `EstimateApprovalTest`, `ApprovalConcurrencyTest`에서 부족·미설정·마감·원장/이력 저장 실패의 전체 롤백, 정확한 잔액 승인, 원장 종류별 잔액 계산, 재전송 시 단일 예약과 실제 동시 승인을 검증했다. 외부 승인 화면은 후속 2.11에서 연결한다.

- [x] **3.6 작업시간 확정 시 예약을 실사용으로 전환한다**
   - 확정할 작업시간만큼 예약을 줄이고 같은 분을 실사용으로 늘린다.
   - 같은 작업기록을 다시 확정해도 원장이 한 번만 생성되어야 한다.
   - 남은 예약보다 많은 시간을 확정하려면 추가 견적 승인을 먼저 받는다.
   - 구현: `ConfirmWorkLog`가 최신 요청·처리자·작업기록·계약월을 잠그고 같은 요청/월의 `reserve - release`를 계산한다. 작업기록 원인(`work_log`, 기록 ID)의 `release`와 `usage`를 같은 분으로 생성한 뒤 확정 상태·시각·수정 버전을 한 트랜잭션에서 반영한다. 원장 처리자 ID로 실제 확정자를 추적하며 일반 모델 저장을 통한 확정은 계속 차단한다.
   - 작성자 또는 최고관리자만 확정할 수 있고 처리 시 권한을 다시 확인한다. 호출자는 확인한 초안의 수정 버전을 전달해야 하며 같은 버전의 확정 재전송은 기존 결과만 반환한다. 다른 요청의 예약, 미승인 견적, 승인 사용월과 다른 작업일, 마감된 월, 완료·취소 요청은 신규 확정에 사용할 수 없다. 작업일은 승인 견적의 사용 대상 월에 속해야 하므로 월을 넘긴 작업은 후속 월 전환·재견적 절차가 필요하다.
   - 범위: 이번 단계는 차감 작업기록의 내부 확정 서비스다. 비차감 기록 확정은 3.10, 입력·확정 화면은 3.13에서 연결하며 외부 API는 추가하지 않았다. 스키마 변경이나 추가 마이그레이션은 없다.
   - 서버 검증(2026-10-03): `WorkLogConfirmationTest`와 `WorkLogConfirmationConcurrencyTest` 신규 **18개 테스트·105단언**으로 동일 분 전환·잔액 유지·재전송·예약 초과·다른 요청 예약 격리·미승인/다른 월/마감/종료 상태 차단·권한 재검사·오래된 초안·호출 객체 변조·원장 및 상태 저장 실패 롤백·확정 후 실제 월 마감과 재전송을 확인했다. 별도 DB 연결에서 같은 기록 동시 확정과 두 기록의 예약 경쟁도 통과했다. 전체 **444개 테스트·2,771단언 통과**, Pint **197파일 통과**, PHPStan **오류 0건**, 빌드 **22모듈 성공**, `git diff --check`와 개발 `/up` HTTP 200을 확인했다. 개발 DB는 기존 마이그레이션 배치 15까지 적용된 상태이며 운영 DB는 변경하지 않았다.

- [x] **3.7 완료와 취소 시 남은 예약을 해제한다**
   - 사용하지 않은 예약시간을 모두 해제한다.
   - 이미 확정된 실사용시간은 자동으로 되돌리지 않는다.
   - 실사용 취소가 필요하면 사유가 있는 별도 원장을 만든다.
   - 구현: `TransitionWorkRequest`의 완료·취소 트랜잭션 안에서 `ReleaseRemainingReservation`이 요청별 `reserve - release`를 다시 계산하고 남은 분 전부를 `release`로 기록한다. 상태, 상태 이력, 활동, 반환 원장은 함께 성공하거나 함께 롤백된다. 승인 후 막아 두었던 취소 버튼과 고객사 관리자의 검수 완료 버튼을 열었으며 완료는 최신 고객 승인 견적이 있을 때만 허용한다.
   - 요청 잠금 순서를 작업시간 확정과 동일하게 유지해 확정 대 취소 경쟁을 직렬화한다. 먼저 확정되면 사용분을 제외한 잔여 예약만 반환하고, 먼저 취소되면 전액 반환한 뒤 확정을 거부한다. 월 전환·재견적은 기존 예약을 먼저 정리한다는 3.8·3.9 규칙에 따라 여러 월에 남은 예약이 동시에 발견되면 자동으로 합치지 않고 정리를 요구한다.
   - `CancelWorkLogUsage`는 확정 작업기록과 원래 `usage` 원장을 보존한 채 동일 분의 `cancel_usage`를 별도로 추가한다. 사유와 실제 처리자를 필수로 남기며, 같은 내용의 재전송은 기존 원장을 반환하고 다른 내용의 재전송·고객 사용자·비활성 처리자·원장 불일치·마감 월은 거부한다. 완료·취소 자체는 이 원장을 자동 생성하지 않는다. 외부 관리 화면은 3.14 원장 화면에서 연결한다.

- [x] **3.8 견적 변경 시 기존 예약을 교체한다**
   - 기존 승인 견적의 남은 예약을 먼저 해제한다.
   - 새 견적 버전을 승인할 때 새 예상시간을 예약한다.
   - 두 동작은 이력과 원장을 통해 각각 추적할 수 있어야 한다.

### 목표

업무에 필요한 자료와 알림을 안전하게 운영하고, 핵심 시나리오와 복구 절차를 검증한 뒤 서비스를 배포한다.

### 첨부파일 구현

- [x] **4.1 첨부파일 데이터와 업무 자료 연결을 구현한다**
   - `attachments` 테이블, `Attachment` 모델과 요청·댓글·견적 버전의 `attachments()` 관계를 추가했다. 요청·고객사 연결은 필수이고 댓글 또는 견적 버전은 최대 하나만 지정한다. 관계 무결성에 필요한 고객사 ID를 이 단계에서 포함했으며 나머지 파일 메타데이터는 4.2에 남긴다. 복합 외래 키와 CHECK 제약으로 타 고객사·타 요청·존재하지 않는 자료와 중복 대상 연결을 DB에서 거부한다.

   - 내용 무결성: 신규 등록 시 파일의 SHA-256을 저장하고 검사 중 다시 계산해 같은 크기의 내용 변경도 실패 처리한다. 다운로드 직전에도 SHA-256을 비교해 검사 뒤 바뀐 파일이 전달되지 않게 한다. 과거 해시 없는 파일은 실제 첫 검사 결과로만 해시를 확정하며 확정된 해시는 모델과 DB에서 변경할 수 없다.

### 운영 승인 전 최종 검사

- 다른 고객사의 요청, 댓글, 견적, 시간 내역, CSV와 파일에 접근할 수 없다.
- 고객사 일반 사용자는 견적 승인, 검수 완료, 월 마감과 조정을 수행할 수 없다.
- 동시 승인으로 사용 가능시간보다 많이 예약되지 않는다.
- 작업시간 재전송으로 이중 차감되지 않는다.
- 취소, 견적 변경, 무상 수정과 월 전환 계산이 모두 자동 테스트를 통과한다.
- 허용되지 않은 파일과 제한 용량을 넘는 파일이 차단된다.
- 알림 실패를 확인하고 안전하게 재시도할 수 있다.
- 데이터베이스와 첨부파일 백업을 실제로 복원할 수 있다.
- 운영 환경에서 디버그 정보와 비밀값이 노출되지 않는다.
- 데모 시나리오 전체를 수동으로 끝까지 실행할 수 있다.

## 개발 작업 우선순위

1. 데이터베이스 구조와 제약조건
2. 모델 관계와 상태 값
3. 정책과 서버 권한 검사
4. 업무 규칙을 처리하는 서비스와 트랜잭션
5. Livewire 화면과 입력 검증
6. 활동 이력과 알림
7. 자동 테스트
8. 실제 브라우저 수동 확인

화면부터 만든 뒤 권한이나 거래 규칙을 나중에 붙이지 않는다. 각 기능은 데이터 제약, 서버 권한, 업무 처리, 화면, 테스트가 한 묶음으로 끝나야 완료로 본다.

## 구현 중 지켜야 할 결정 규칙

- 요구사항이 기존 합의 범위를 벗어나면 원 요청을 수정하지 않고 연결된 새 요청과 새 견적으로 처리한다.
- 승인된 견적을 바꿔야 하면 새 견적 버전을 만들고 다시 승인받는다.
- 예산과 일정이 현실적으로 불가능하면 무리하게 진행하지 않고 가능한 범위와 일정을 다시 제안한다.
- 고객의 새 요구, 외부 서비스 변경, 고객 환경 변경은 기본적으로 유상 작업으로 본다.
- 최초 합의한 기능이 다르게 작동하면 무상 수정 후보로 기록하고 관리자와 개발자가 원인을 확인한다.
- 주요 업무 장애는 일반 요청보다 먼저 처리하고 1시간 안에 최초 응답한다.
- 여러 일반 요청은 긴급도, 접수 순서, 납기일 순서로 처리한다.
- 확인하지 않은 완료일과 복구시간을 고객에게 약속하지 않는다.
- 버그나 일정 지연 위험이 생기면 영향과 대응 계획을 먼저 정리하고 예정일 전에 고객과 협의한다.

## 전체 구현 완료의 정의

Approid Desk의 첫 운영 버전은 다음 조건을 모두 만족할 때 완료로 본다.

1. 요청 접수부터 견적, 승인, 계약 확인, 개발, 검수와 완료까지 한 시스템에서 처리할 수 있다.
2. 고객사별 데이터가 서버 권한과 데이터베이스 관계를 통해 분리되어 있다.
3. 제공시간, 예약시간, 실사용시간과 반환시간을 분 단위 원장으로 재현할 수 있다.
4. 승인된 견적과 마감된 시간은 덮어쓰지 않고 변경 이력으로 남는다.
5. 댓글, 파일, 작업기록, 승인, 상태 변경과 고객 확인 자료가 요청에 연결되어 있다.
6. 자동 테스트와 수동 검수가 끝났으며 실제 업무를 막는 장애가 없다.
7. 알림 재시도, 백업, 복원과 롤백이 검증되어 있다.
8. 데모 시나리오와 고객사 간 접근 차단을 반복해서 시연할 수 있다.
