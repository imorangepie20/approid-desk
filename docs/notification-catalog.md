# Approid Desk 업무 알림 카탈로그

## 목적과 적용 범위

이 문서는 업무 사건을 알림으로 변환할 때 사용하는 안정적인 타입, 수신 그룹, 중요도와 기본 채널을 정의한다. 공통 수신자 조회와 데이터베이스 저장, 큐 이메일 발송은 `NotificationRecipients`, `SendBusinessNotification`, `BusinessNotification`을 통해 처리한다.

알림 타입은 `App\Enums\NotificationType`, 수신 그룹은 `NotificationAudience`, 중요도는 `NotificationPriority`, 기본 채널은 `NotificationChannel`을 기준으로 한다. 저장된 `kind`에는 enum의 영문 값을 사용하고 화면과 메일에는 한글 라벨을 사용한다.

## 수신 그룹

| 그룹 | 해석 규칙 |
| --- | --- |
| `operations` | 활성 최고 관리자와 운영자 중 작업공간에 접근할 수 있는 계정 |
| `company_admins` | 사건이 속한 고객사의 활성 고객사 관리자 |
| `request_submitter` | 요청을 등록한 활성 사용자 |
| `request_assignee` | 요청에 지정된 활성 담당자 |
| `request_stakeholders` | 요청 등록자, 담당자와 댓글 작성자 중 해당 요청을 현재 조회할 수 있는 활성 사용자 |
| `attachment_uploader` | 첨부파일을 등록했고 해당 첨부를 현재 조회할 수 있는 활성 사용자 |

수신자를 해석할 때는 최신 계정·고객사 활성 상태와 대상 자료 조회 권한을 다시 검사한다. 여러 그룹에 속한 사용자는 한 번만 포함하고 행위를 일으킨 사용자는 기본적으로 제외한다. 고객사 자료는 다른 고객사 사용자에게 발송하지 않는다.

## 페이로드와 보안 규칙

- 모든 알림은 `kind`, `message`, `action_url`과 수신자가 접근할 수 있는 최소 식별자만 저장한다.
- 요청 범위 알림은 고객사 ID와 요청 ID를 포함하고, 이동 시 현재 사용자 권한을 다시 검사한다.
- 메일과 데이터베이스 페이로드에 요청 본문, 댓글 원문, 견적 내부 메모, 파일 내용·저장 경로, 검사기 오류 원문, 접속정보와 토큰을 넣지 않는다.
- 감염 알림은 원본 파일명과 안전한 검사 결과만 표시하며 저장 경로나 파일 다운로드 링크를 제공하지 않는다.
- 첨부 검사 실패는 고객에게 내부 장애 원인을 공개하지 않고 처리가 지연되었다는 안전한 문구만 제공한다.
- 기본 채널은 정책 기준이다. 실제 발송은 데이터가 커밋된 뒤 큐에서 처리하며, 자동·수동 재시도와 사건별 중복 방지는 전달 원장을 기준으로 처리한다. 최종 실패 확인과 운영자 재시도도 같은 전달 건을 갱신한다.

## 발송 처리

- 요청 생성, 주요 장애 대응·롤백 기록, 담당자 변경, 댓글, 견적 제출·승인·수정 요청, 작업 상태 전환, 첨부 검사와 월 전환 사건은 공통 발송기로 연결한다.
- `BusinessNotification`은 `ShouldQueueAfterCommit`을 구현한다. 데이터베이스 채널과 메일 채널은 각각 큐 작업으로 분리되며, 아직 커밋되지 않은 업무 데이터를 발송하지 않는다.
- 각 알림 채널 작업은 최초 실행을 포함해 최대 4회 시도하고 실패 뒤 60초, 300초, 900초 순서로 기다린다. 한 번의 실행은 최대 30초이며 시간 초과도 해당 시도를 실패로 끝낸다.
- 데이터베이스 큐의 `retry_after`는 90초다. 알림의 30초와 첨부 검사의 60초 실행 제한보다 길어 처리 중인 작업이 가시성 만료로 동시에 다시 실행되지 않게 한다. Compose 워커의 일반 제한은 75초이며 작업별 제한이 우선한다.
- 각 업무 사건은 원인 자료와 알림 타입을 해시한 사건 키를 사용한다. 같은 사건·수신자·채널 조합은 `notification_deliveries`에 한 번만 예약하며, 채널 성공 뒤에는 같은 전달 작업을 다시 실행하지 않는다. 채널 예외가 나면 완료 처리하지 않아 기존 큐 재시도를 허용한다.
- DB 알림 ID는 전달 ID로 고정해 알림 저장 뒤 큐 응답만 유실된 경우에도 중복 행을 만들지 않는다. 메일은 같은 전달 ID의 `Message-ID`를 유지하지만 외부 SMTP 수신과 내부 DB 기록을 원자적으로 묶을 수는 없다. 최종 실패 화면에서 전달 상태와 시도를 확인한 운영자가 이 불확실성을 고려해 같은 전달 건을 재시도한다.
- 수신자는 발송 요청 때 활성 상태, 고객사 경계와 자료 조회 권한을 검사한다. 큐 실행 때도 같은 조건을 다시 검사해 그 사이 비활성화되거나 권한을 잃은 계정에는 보내지 않는다.
- 허용 목록에 있는 사건 식별자만 페이로드에 더한다. 수정 요청 사유, 댓글 본문, 파일 저장 경로와 검사 오류 원문처럼 민감하거나 불필요한 값은 호출자가 넘겨도 버린다.
- 주요 장애 대응 알림은 불변 대응 이력 ID만 사건 식별자로 사용한다. 실제 대응·협의 상세는 알림 페이로드에 복제하지 않고 권한이 다시 확인되는 요청 상세에서만 조회한다.
- 주요 장애 롤백 알림은 롤백 ID와 시작·완료 단계만 사건 식별자로 사용한다. 실행·검증 계획과 결과 원문은 알림에 복제하지 않고 권한이 다시 확인되는 요청 상세에서만 조회한다.
- 주간 진행 보고는 매주 월요일 09:15에 직전 월요일 00:00부터 일요일 23:59까지를 회사별로 집계한다. 활성 회사 중 현재 열린 요청이 있거나 해당 기간에 신규 요청 또는 상태 변경이 있는 회사만 대상으로 하며, 열린 요청의 상태별 수와 신규·상태 변경·완료 요청 수를 불변 스냅샷으로 보존한다.
- 주간 보고는 활성 운영 계정과 해당 회사의 활성 고객사 관리자에게 DB·메일로 발송한다. 고객사 일반 사용자와 다른 회사 고객 계정은 제외하며 큐 실행 시 최신 역할·회사 활성 상태를 다시 검사한다.
- 같은 회사·같은 주차에는 하나의 `weekly_progress_reports`만 생성하고 보고 ID 기반 사건 키로 수신자·채널별 전달을 한 번만 예약한다. 보고 스냅샷은 수정·삭제할 수 없으며 채널별 성공·실패·수동 재시도는 기존 `notification_deliveries`와 불변 재시도 이력에 남긴다.
- 전달 원장은 상태, 시도 횟수, 마지막 시도와 최종 실패 시각, 안전한 실패 코드만 기록한다. 예외 원문과 SMTP 인증정보는 저장하지 않는다.
- 운영자와 최고 관리자만 최종 실패 목록을 조회하고 수동 재시도할 수 있다. 저장된 최소 페이로드, 활성 수신자와 현재 요청 조회 권한을 다시 검사하며 재시도 요청자·시각은 불변 감사 기록으로 보존한다.
